# 루플레 프로젝트 상세 인계 (2026-10-27)

루플레는 사용자의 이동 근거를 바탕으로 루틴을 먼저 제안하고, 승인한 루틴의 준비·알림·차량 실행을 연결하는 개인화 모빌리티 플랫폼입니다. 출퇴근뿐 아니라 몇 달에 한 번 방문하는 장소까지 챙기는 것이 핵심 가치입니다. 현재 제품·논리 모듈·제출 추진 기준은 GitHub에 공유했고, Pleos 에뮬레이터의 최소 내비 검증 앱을 구현했습니다. 최신 작업 지점은 모듈별 수직 개발과 Kubernetes 기반 마이크로서비스 아키텍처(MSA)에 맞는 애플리케이션 아키텍처(AA)를 확정하고 구현 전제를 검증하는 단계입니다. 프레임워크는 선정했으며 제품 서버 구축·클러스터 배포는 아직 완료하지 않았습니다.

> 이 문서는 2026년 10월 27일 Tramen에 저장한 상세 인계를 바탕으로 작성한 팀 공유본입니다. 개인 작업 경로·기록 식별자는 제외하고, AA 문서의 게시 상태와 재개 경로를 이번 공유에 맞춰 갱신했습니다. 원래 인계 시점에 로컬에만 있던 AA 초안은 이후 공유됐고, 같은 날 사용자 확인을 반영해 [AA 확정본](../architecture/application-architecture.md)으로 전환했습니다. 기술 선정과 제품 구현 완료는 구분합니다.

## 1. 기록 목적·출처·확인 상태

- 분류: 개인 프로젝트. 사용자가 다른 세션에서 즉시 이어갈 수 있도록 상세 기록을 명시적으로 요청했습니다.
- 기록 기준: 2026년 10월 27일 한국 시각. AA 초안의 기준일은 10월 26일이고 확정일은 10월 27일입니다.
- 목적: 다음 세션이 제품 방향과 검증 결과를 다시 묻거나, 확정한 AA와 미완료 실행 검증을 섞지 않고 구현 전제 확인부터 시작할 수 있게 합니다.
- 출처: 이번 대화의 사용자 지시·답변, 로컬 레포와 Git 상태, 커밋된 설계·검증 문서, Tramen 인프라 기록입니다. 새로운 제품 비전·기본 임계값·성능 목표는 추가하지 않았습니다.
- 확인 축: 사용자 지정·기존 합의와 AI 추천을 본문에서 구분했습니다. 2026년 10월 27일 사용자가 AA 추천 구성을 채택하고 Gemma 4 멀티모달 모델을 우선 적용하도록 확인했습니다. 이 인계문 전체의 별도 확인과 실제 구현 검증은 아직입니다.
- 이번 공유 범위: AA 확정본, 이 상세 인계, 오늘의 논의 기록과 문서 진입점입니다. 제품 코드·SDK 결과·클러스터는 변경하지 않습니다.

## 3. 사용자와 합의한 제품 가치와 진입 흐름

루틴을 사용자가 일일이 입력하는 방식이 기본이 아닙니다. 앱이 근거가 있는 장소와 이동을 먼저 발견하고 ‘이 이동을 루틴으로 관리할까요?’라고 제안합니다. 수동 생성은 당연히 제공하되 보조 진입점으로 둡니다.

1. 차량 앱·스마트폰 어디서든 시작할 수 있습니다. 구체적인 가입·기기 연결·동의 화면과 계정 정책은 상세 설계가 필요합니다.
2. 확보 가능한 집·회사·즐겨찾기 등 유효한 등록 장소를 우선 근거로 사용합니다. 등록 장소만으로 방문 주기나 의도를 확정하지 않습니다.
3. 등록 장소가 없으면 반복 방문·추가 이동 근거가 쌓인 뒤 제안합니다. 근거 없는 장소를 한 번 방문했다는 이유만으로 즉시 루틴 등록을 묻지 않습니다.
4. 데이터가 전혀 없으면 기다리면서 선택적인 수동 등록 경로를 제공합니다. 데이터 부재·조회 실패·미지원·동의 거부는 서로 다른 상태입니다.
5. 후보와 이유·확인할 주기를 제시하고 사용자가 수정·승인한 뒤 루틴을 활성화합니다. 제안 수락과 개별 차량 동작 승인의 의미는 구분합니다.
6. 이후 실행·거절·수정·연기와 실제 관찰을 축적해 개인별 제안과 알림을 보완합니다. 무응답을 거절·완료로 간주하지 않습니다.

출퇴근, 아이 등하교·학원, 정기 병원·치과, 미용실, 정비소 등의 사용자 사례가 이미 제시됐습니다. 다음 세션에서 대표 시나리오를 처음부터 다시 요구하지 않습니다. 상세 시험값·주기 판정 기준·정책을 결정할 때만 부족한 부분을 질문합니다. ‘3개월마다 방문’ 같은 값은 사용자 설명의 예시이며 제품 기본값으로 확정한 것은 아닙니다.

단기·중기·장기 주기와 조건부 이동, 사전 준비·알림, 목적지·경로 추천, 승인 기반 내비 연계가 제품 범위입니다. 일정·예약 자료와 실제 방문 사실도 구분합니다.

## 4. 차량·스마트폰·서버 역할과 네 입출력 경로

차량 Pleos 앱이 제품의 중심입니다. 스마트폰 컴패니언 앱은 제안·조회·수정·삭제, 실행 진행 확인, 알림 등 루틴을 사용자에게 보여주고 관리하는 역할을 수행합니다. 차량 앱에는 같은 관리·표시 기능과 함께 지원되는 차량 실행 어댑터가 추가됩니다.

- 차량·스마트폰: 엣지 클라이언트(Edge Client)
- 중앙 애플리케이션 서버: 자동화 허브(Automation Hub), 상태·제안·루틴·판정·작업 조정
- 입력 기기와 출력 기기는 독립입니다. 출력 기기가 차량 실행 주체를 바꾸지는 않습니다.

| 입력 기기 | 결과 표시 기기 | 차량 동작이 포함될 때의 실행 주체 |
| --- | --- | --- |
| 스마트폰 | 스마트폰 | 차량 앱이 SDK 실행, 스마트폰에 진행·결과 표시 |
| 스마트폰 | 차량 앱 | 차량 앱이 표시·SDK 실행 |
| 차량 앱 | 스마트폰 | 차량 앱이 SDK 실행, 스마트폰에 진행·결과 표시 |
| 차량 앱 | 차량 앱 | 차량 앱이 표시·SDK 실행 |

```text
차량 또는 스마트폰의 입력·관찰
  → M1 출처·시각·이용 범위를 갖춘 근거
  → M2 패턴·계산·후보·설명
  → 선택한 기기에 제안 표시
  → 사용자 수정·승인
  → M3 승인 루틴·버전 저장
  → M4 조건 확인·실행 계획·알림 조정
  → M5 지원 여부와 승인 확인 후 차량 실행
  → M6 양쪽 기기에 진행·결과·미확인 상태 표시
  → 새 관찰·사용자 반응을 M1·M2에 반영

수동 생성은 M3 진입 경로입니다.
음성·터치·보조 채팅은 같은 명령 검증 경계를 사용합니다.
🚧 계정 연결·재승인·기기 오프라인·만료 정책은 상세 계약에서 확정합니다.
```

알림 전달 성공, 사용자 확인, 내비 요청 수락, 경로 탐색 완료, 실제 도착·정비·주유 완료는 각각 다른 상태입니다. 후속 관찰 없이 완료를 확대 해석하지 않습니다.

## 5. 전체 제품 확장 방향과 현재 권한의 경계

사용자는 이동 루틴과 상태형 차량 관리를 함께 묶는 방향에 동의했습니다. 주유·전기차 배터리, 워셔액 부족, 타이어 저압, 정비·누적 거리, 문·창문, 온도·날씨 등의 상태를 개인의 이동·승하차·주유·관리 패턴과 결합합니다. 알림 시기·빈도·중복·연기를 개인화하는 것이 차별점입니다. 개별 템플릿·임계값·중요 경고 예외는 미정입니다.

캘린더의 일정·장소 연계도 전체 안건에 포함합니다. Google Calendar의 자유 형식 장소는 식별·좌표 확인이 필요하며 캘린더 일정이 실제 이동·방문 증거는 아닙니다. 계정 자료를 실제로 읽거나 OAuth 연결을 구현한 상태는 아닙니다. 마이현대 정비 예약 연계도 희망 사항이며 공개 접근·권한·실제 연동은 미검증입니다.

사용자의 실제 주행 경로와 과거 소요 시간을 기억해 익숙한 길·지름길과 내비 추천을 비교하는 방향이 제시됐습니다. 전체 도로 경로를 그대로 주입하기 어렵다면 경유지로 유사 경로를 구성하는 타협안을 사용자가 수용했습니다. 경유지로 완전히 같은 경로를 보장하지 않습니다. 과거 실측 시간과 현재 교통 기반 예상시간도 구분합니다.

장기 비전은 개인화 모빌리티 맥락(Mobility Context) 데이터 계층입니다. 허용된 근거·승인·반응·실행과 관찰이 쌓이면 개인별 목적·시기·선호를 더 잘 설명하고 추천할 수 있다는 방향입니다. 자동으로 자율주행 데이터가 완성되거나 모델 학습이 완료됐다는 주장은 아닙니다.

- 현재 제품: 개인별 이동·상태·루틴·반응의 근거와 이력을 연결하고 추천·실행을 지원
- 향후 권한 확대 전제: 제조사 협력·허용 범위 확보 후 에너지·파워트레인 관리, 자율주행 개인화 데이터와 연계 검토
- 장기 사업 확장: 별도 동의와 이용 범위 아래 집단 추천, 사라진 장소의 대체 추천·광고 검토

엔진 시동·예열·공조 원격 제어·카메라·자율주행 제어를 현재 가능하다고 확정한 적은 없습니다. 현재 준비 제안과 실제 제어는 분리합니다.

## 6. 논리 모듈과 모듈별 개발 원칙

| 모듈 | 소유 책임 | 주요 경계 |
| --- | --- | --- |
| M1 근거·맥락 | 장소·이동·차량·일정 등 관찰, 출처·시각·신선도·이용 범위 | 관찰 사실과 추정을 구분 |
| M2 패턴·추천 | 통계·계산·개인 패턴·후보·SLM 해석·설명, 제안 반응 | 승인 루틴을 직접 변경하지 않음 |
| M3 루틴 관리 | 승인·수동 생성·조회·수정·삭제, 정의·버전 | 상태 변경의 소유자 |
| M4 자동화 판단 | 유효한 근거·조건·루틴 버전 확인, 실행 계획·작업·알림 정책 | 수정·삭제 후 오래된 작업 실행 방지 |
| M5 차량 실행 | SDK·지원 기능·기기 상태·요청 검증·실행·결과 보고 | 허용된 차량 동작만 수행 |
| M6 상호작용·전달 | 기기별 카드·명령·알림·진행·반응 연결, 음성·보조 채팅 공통부 | 전달과 실제 실행 성공을 구분 |

규칙 엔진과 AI 패턴 엔진은 분리합니다. 상태를 소유한 모듈이 변경하며 다른 모듈은 계약으로 요청합니다. M6가 모든 화면을 대신 개발하는 구조가 아닙니다.

사용자는 프론트엔드·백엔드 전문 분야별 배정 대신, 한 사람이 자기 모듈의 화면·서버·저장·시험을 경험하는 수직 개발을 원합니다. 후배의 경험 확보도 목적입니다. 진민은 아키텍처 설계·화면 명세·통합 검토를 주도하며 이 시간도 개발 가용 시간에 포함합니다.

- A: M1+M2, 근거·개인 제안의 화면·서버·저장·시험
- B: M3+M4, 승인·CRUD·규칙·작업·알림의 화면·서버·저장·시험
- C: M5+M6, 차량 브리지·실행·공통 상호작용·전달과 해당 화면
- 🚧 실제 사람별 배정은 미정입니다. 풀타임 인력이 C를 우선 검토하는 안과 실명 배정은 구분합니다. 풀타임 인력을 진민으로 추정하지 않습니다.

## 7. AI·음성·생성형 UI의 합의 방향

사용자가 말한 로컬 소형 언어 모델(SLM)은 팀이 직접 운영하는 서버 안에서 실행하는 구상입니다. 차량·스마트폰 내부 추론을 필수로 확정한 것이 아닙니다. DGX Spark 사용 가능은 사용자 확인이며 실제 모델·접근·메모리·지연은 미측정입니다.

수치 계산·통계·조건 판정은 프로그램이 수행하고, SLM은 관련 맥락 해석·후보 설명·표현 구성·의도 해석을 지원합니다. 사용자별 명시 설정과 축적된 프로필·근거를 입력으로 활용하며 사용자마다 모델을 자동 재학습하는 방식은 확정하지 않았습니다.

모델 출력은 후보 ID·근거·버전·허용 행동·필수 인자를 검증한 뒤 제안으로 사용합니다. 모델이 권한을 만들거나 DB 상태를 직접 변경하거나 차량 제어를 바로 호출하지 않습니다. 근거 부족은 확인 질문으로 드러냅니다.

음성 입력·출력, 생성형 사용자 인터페이스(Gen UI)의 카드, 보조 채팅을 전체 제품 방향으로 채택했습니다. 차량은 운전 중 음성·간단한 카드가 중요하며 스마트폰과 차량의 화면 구성을 같게 고정하지 않습니다. Gen UI는 등록된 컴포넌트·동작을 스키마로 선택하는 형태이며 임의 코드·스크립트를 생성해 실행하지 않습니다. ‘첫 번째로 해줘’ 같은 발화는 현재 화면·후보·버전에 연결해야 합니다.

모델 장애 시 기본 규칙·고정 카드 경로를 유지하는 방향입니다. 이것이 서버 단절·차량 앱 종료·원격 기동까지 해결했다는 의미는 아닙니다. Gleo의 앱 함수 연계와 별도 음성 인식·합성 어댑터는 구분하며 실제 기기 시험이 필요합니다.

## 8. 최신 사용자 지시와 AA 확정 상태

사용자는 구체적인 모듈 입출력 계약 전에 프론트엔드·백엔드·DB·서버 환경을 포함한 AA를 먼저 검토하자고 지적했습니다. 대표 시나리오는 이미 대화에 제시돼 있으므로 재질문을 반복하지 않습니다.

최신 사용자 지정은 다음과 같습니다.

- 모듈별로 각자 화면까지 개발할 수 있는 구성
- 이미 설치한 Raspberry Pi 5 Kubernetes 환경을 활용하는 MSA 검토
- 빠른 개발을 위한 모바일 웹 허용, 네이티브 앱 고집하지 않음
- 팀 서버 AI에 생성 모델뿐 아니라 임베딩·검색 증강 생성(RAG) 등 부가 계층 포함

이는 이전 문서의 ‘초기 작은 단일 백엔드’ 기준을 변경하는 지시입니다. 전체 제품 목적·M1~M6·네 경로·필수 기능은 유지합니다. 과거 문서를 이유로 최신 MSA 지시를 무시하지 않습니다. 아래 기술 선택은 2026년 10월 27일 사용자 확인으로 확정됐으며 실제 호환·성능·배포 결과는 후속 검증합니다.

| 영역 | 확정 기준 | 검증·미정 사항 |
| --- | --- | --- |
| 모노레포 | pnpm workspace + Nx | 언어 숙련도·도구 호환·패키지 버전 |
| 화면 | React + Vite + TypeScript, TanStack Query, Tailwind CSS + shadcn/ui | 차량 규격·WebView 지원·화면 명세 |
| 스마트폰 | 설치형 웹 앱(PWA) | Android·iPhone 설치·푸시·마이크·복구 시험 |
| 차량 | Capacitor Android 호스트 + Kotlin/Java Pleos 플러그인, 번들한 웹 화면 | Pleos SDK·화면 전환·수명주기·운전 중 제한·심사 호환 |
| 차량 대안 | Kotlin Compose 차량 화면 | 웹 호스트 부적합 시 전환, 데이터 계약·토큰 공유 |
| 업무 서버 | NestJS + FastifyAdapter + TypeScript | Pi 실제 자원·팀 경험 검증. Go도 대안이며 Repair의 Go 선택을 루플레 결정으로 승계하지 않음 |
| DB | PostgreSQL + Drizzle, 서비스별 논리 DB·런타임 역할·마이그레이션 | 물리 인스턴스·주 버전·백업·운영 권한 |
| 검색 | PostGIS 공간 조회, pgvector 의미 검색 | 지도 매칭·길찾기 자체 구현으로 오해하지 않음 |
| 작업 | PostgreSQL outbox + pg-boss 워커 | 재시도·멱등·만료·삭제와 실행의 경쟁 처리 |
| AI 응용 | FastAPI + LlamaIndex, DGX Spark의 vLLM, Gemma 4 12B IT | 멀티모달 입력·한국어 품질·컨테이너·지연·동시 처리량 |
| 배포 | 기존 k3s + Argo CD + Kustomize, ARM64 이미지 | 여유 자원·네임스페이스·스토리지·Ingress·승인 절차 |

세 업무 서비스의 제안 경계는 A `context-api`(M1·M2), B `automation-api`와 worker(M3·M4), C `interaction-api`(M5·M6, 기기 연결·프론트 집계/BFF)입니다. AI는 별도 `ai-api`와 추론 런타임으로 분리합니다. 논리 모듈마다 서비스 하나를 무조건 만드는 안은 아닙니다.

프론트는 하나의 웹 앱으로 조립하되 A·B·C별 기능 패키지·화면 경로를 소유합니다. 초기부터 런타임 마이크로 프론트엔드를 필수로 두지 않습니다. 공통 계약·컴포넌트·명령 경계는 공유하고 다른 서비스 DB 직접 쓰기·공유 ORM 모델·교차 DB 조인으로 결합하지 않습니다.

```text
스마트폰 PWA / 차량 Android 호스트
  ↔ Ingress ↔ C interaction-api
                 ↔ A context-api
                 ↔ B automation-api + worker
                 ↔ ai-api(음성·공통 의도 해석)
A context-api ↔ ai-api(검색·근거·설명)
ai-api ↔ GPU의 생성·임베딩·선택한 음성/재순위 런타임
A·B·C ↔ 각자 소유하는 DB·outbox
B 실행 작업 → C → 차량 브리지 → Pleos SDK → 결과 보고
🚧 실제 플랫폼/개인 서버 배치와 GPU 접속·인증·가용 자원은 미검증
```

C의 음성·의도 해석 요청을 모두 A에 우회시키지 않습니다. A는 RAG 근거의 소유자이고 C는 현재 화면·후보·허용 목적을 포함해 AI에 직접 요청할 수 있습니다. 해석된 명령은 다시 소유 도메인의 검증을 거칩니다.

동기는 REST·OpenAPI, 비동기는 생산 서비스 DB outbox와 상대 API 재전달을 추천합니다. 루틴마다 Kubernetes CronJob을 만드는 대신 앱 워커에서 예약·재시도를 처리합니다. 큐의 전달 보장이 차량 SDK의 물리적 1회 실행을 자동 보장하지는 않습니다.

제안한 디렉토리는 `apps/web`, `apps/car`, `apps/context-api`, `apps/automation-api`, `apps/automation-worker`, `apps/interaction-api`, `apps/ai-api`, `packages/{context,automation,interaction}`, `packages/presentation`, `packages/platform`, `infra/k8s`입니다. 이 구조의 제품 스캐폴딩·의존성 설치·DB 생성·이미지 빌드·배포를 완료한 상태는 아닙니다.

### 임베딩·RAG 처리안

허용된 사용자 표현·명시 선호·패턴 요약을 출처·계정·차량·목적·유효기간·버전과 함께 준비하고 필요한 자료만 벡터화합니다. SQL의 최신 사실과 의미 검색을 조합하고 필요하면 재순위한 뒤 맥락을 구성합니다. 생성 결과는 구조화·검증해 제안으로 반환합니다. 원시 센서·좌표를 전부 텍스트로 바꾸어 계속 모델에 보내거나, 검색 결과를 현재 차량 상태의 정답으로 취급하지 않습니다.

다른 사용자 자료가 섞이지 않도록 검색·프롬프트 범위를 확인하고, 삭제·동의 철회 시 원문·요약·벡터·캐시를 함께 갱신·제거해야 합니다. AI DB 권한은 A 소유 검색 자료의 제한된 역할로 둡니다.

생성·멀티모달 이해 모델은 Gemma 4 12B IT로 확정했습니다. 텍스트·이미지·오디오를 입력받아 텍스트로 응답하며, 음성 합성은 제공하지 않으므로 TTS는 별도 모델이 필요합니다. 임베딩 초기 후보 Qwen3-Embedding-0.6B는 생성 모델과 별개이며, 실제 한국어 장소 검색·DGX 성능을 측정한 선정 결과는 아닙니다. 재순위·TTS 모델도 미정입니다. 외부 기본 모델 제공자가 예제 설정으로 연결되지 않도록 자체 호스팅 제공자를 명시해야 합니다.

AA 문서는 별도 검토자가 확인했고 C와 AI의 음성 경로 누락을 보완한 뒤 재검토했습니다. 문서 링크·공백·민감정보 검사는 수행했지만 제품 실행·차량 웹 호스트·클러스터 적합성을 검증한 것은 아닙니다.

## 9. 실제 구현·시험 완료 범위

실제 구현은 `prototypes/pleos-nav-probe`의 최소 Android 검증 앱입니다. 제품의 스마트폰·서버·루틴 엔진·AI 통합은 아직 구현 완료가 아닙니다. SDK 시험 결과·해석은 원문 문서상 진민 확인 전이며, 1차 세부 완료 기준·증빙도 검토안입니다. 사용자가 검증 범위·핵심 기능을 지정한 사실과 결과·상세 기준을 확인한 상태는 구분합니다.

근거는 `docs/research/pleos-nav-probe-results.md`, 최신 `docs/research/pleos-navigation-execution.md`와 `docs/research/results/`의 공개 요약입니다. 최신 내비 실행 시험은 2026년 10월 26일, 실행 식별자 `20261026T075534Z-nav-execution-final`입니다.

시험 환경: Pleos Connect 2.1.0/API 34 ARM64 AVD `Ruple_Pleos_2_1`, 검증 앱 `com.ruple.probe` 0.2.1, NaviHelper 3.0.5, navi-data 3.0.4, 내비 서비스 3.0.4, 내비 앱 3.3.2-rc5-hotfix.3입니다. Automotive의 실제 현재 사용자는 시험 당시 10이므로 user 0을 고정하면 안 됩니다. 재실행 시 현재 사용자를 먼저 확인합니다.

| 실제 시험 | 관찰 | 확대 해석하지 않을 범위 |
| --- | --- | --- |

| 내비 화면 | `requestNavigationScreen(Foreground)` 뒤 전경 Activity와 스크린샷 변화 독립 확인 | 함수 반환만으로 성공 판정한 것이 아님 |

시험 앱 권한에서 NAVI_ROUTE·NAVI_ROUTE_SEARCH·NAVI_CUSTOM_MAP의 granted 상태를 확인했습니다. 이를 실차·다른 계정·일반 차량 제어 권한으로 확대하지 않습니다. `isRouting=false`와 `ROUTE_GUIDING`이 동시에 관찰됐으므로 isRouting 하나로 안내 활성 여부를 판정하지 않습니다.

빌드·lintDebug·호스트 검사는 당시 통과했습니다. 이후 문서 검토에서 다시 에뮬레이터를 실행하거나 SDK를 재호출한 것은 아닙니다. 나중의 제한 셸에서 adb 바인딩·일부 하드웨어 조회·emulator 버전 호출이 실패한 사실은 호스트 고장이나 설치 부재의 증거가 아닙니다. 재기동 가능 여부는 정상 개발 환경에서 재확인해야 합니다.

원본 화면·위치 로그는 Git 제외 경로 `local-artifacts/pleos-nav-probe/`에 보관하고 공개 레포에는 요약·재현 스크립트를 둡니다. 임시 SDK 추출물은 정본으로 삼지 않습니다.

## 10. 문서 확인과 실제 호출을 구분할 미검증 목록

문서 확인 기준은 기존 10월 26일 조사 스냅샷입니다. 다음 세션은 연동 전에 공식 접근 안내와 프로젝트 권한을 다시 확인해야 합니다.

- NaviHelper 즐겨찾기·최근 목적지·단일 목적지 요청·화면·취소는 위 환경에서 실제 시험했습니다. 위치 이력·실제 도착·주행 경로 전체·방문 시각/횟수는 확보 완료가 아닙니다.
- 경유지 좌표 입력은 문서상 근거가 있습니다. 추가 API의 FIRST/SECOND와 최대 두 경유지 표기, 일괄 요청 제한, 좌표만 있고 POI ID가 없는 입력, 실제 유사 경로 재현은 별도 검증 대상입니다.
- 연료·배터리·워셔액 부족·타이어 저압·누적 거리·문·창문·공조 등의 API 항목은 문서 조사와 실제 호출을 구분합니다. 신규 차량 상태 getter를 실제 시험한 상태는 아닙니다. 워셔액 경고는 사용량·분사 횟수, 저압 경고는 공기압 수치, 오일 수준은 교체 수명과 같지 않습니다.
- SDK 접근 안내의 Vehicle State·NaviHelper와 FusedLocation·STT·TTS·Vehicle Control 준비 상태를 구분합니다. 상세 API 문서가 있다고 해당 계정의 현재 사용 권한을 확정하지 않습니다.
- Gleo 앱 함수 연계 문서의 앱 등록 함수 최대 3개·스키마 심사 안내를 확인한 수준입니다. 실제 음성 호출 시험을 완료하지 않았습니다. Intent 직접 호출 시험만으로 음성 연동을 증명할 수도 없습니다.
- 마이크·오디오 포커스·운전 중 UX 제한·앱 종료·백그라운드·부팅·키오프·휴대폰에서의 차량 원격 기동은 미검증입니다.
- Google Calendar·날씨·유가·경로 제공자의 키·계정·제한·약관·실제 응답은 별도입니다. 외부 API가 공개돼 있다는 사실을 실제 연결 완료로 바꾸지 않습니다.
- Pleos 자료의 추출·저장·서버 전송·모델 입력·시험 결과 공개·SDK 포함 APK 배포 범위는 공식 확인이 필요합니다. 문서의 제한 조항 적용 범위 검토이며 위법 여부를 판정한 것은 아닙니다. 사용자 동의와 제공자 허용은 별개입니다. 원시 데이터·요약·모델 입력별로 확인할 수 있습니다.

## 12. 기존 인프라 기록의 연결과 적용 한계

사용자는 parasix-repair 때문에 Raspberry Pi 5에 Kubernetes를 설치했다고 설명했습니다. 앞선 AA 검토에서 Tramen의 Pi ARM k3s·Argo CD·PostgreSQL 구축 기록을 조회했습니다. GPU는 Pi와 분리하는 방향의 기록이 있습니다. 이번에 아래 두 결정의 타기를 다시 확인했으며 반환된 v1 이웃에는 번복 표식이 없었습니다. 개인 기록의 v2 연결과 라이브 상태까지 확인한 것은 아닙니다.

- 기존 운영 결정 D-infra-18: DB 볼륨 Retain 저장소 종류와 준비 확인 보강. Retain은 백업·복원 성공의 증거가 아닙니다.
- 기존 운영 결정 D-infra-19: Argo CD 출처 무결성 strict·사용자 봉인 절차. 루플레 배포도 기존 승인·출처 관리 절차를 따라야 합니다.

현재 Pi의 여유 CPU·메모리·스토리지·Ingress·스토리지 클래스·기존 부하와 DGX 런타임·모델·접속·동시 추론은 미실측입니다. 과거 장비 수치·계획을 현재 가용량으로 복사하지 않습니다. 루플레의 네임스페이스·DB·역할·리소스 예산을 따로 정하고 Repair DB·Secret을 기본 재사용하지 않습니다. 기존 클러스터에 루플레를 실제 배포한 적은 없습니다.
