# Ruple 담당 경계

두 개발자는 공개 계약을 기준으로 독립적으로 작업합니다. 구체적인 내부 아키텍처와 구현 방식은 각 담당자가 정하고, 프로젝트 책임자는 사용자 흐름과 모듈 입출력을 확정합니다.

## 담당 구분

| 구분 | 담당 범위 | 주요 모듈 | 공동 검토가 필요한 변경 |
|---|---|---|---|
| 트랙 A | 상황 수집과 추천 근거 생성 | M1 상황 수집, M2 상황 해석, 인공지능·검색 증강 생성 연계 | 추천 후보 계약, 개인정보 경계, 모델 입출력 |
| 트랙 B | 루틴 관리와 실행 경험 | M3 루틴 관리, M4 실행 판단, M5 실행 오케스트레이션, M6 상호작용, 웹·차량 셸 | 실행 명령 계약, 사용자 확인 정책, 차량 연동 |
| 프로젝트 책임자 | 대표 흐름과 공개 계약 | 계약 카탈로그, 사용자 상태 전이, 구조 결정 | 모든 계약 및 구조 변경 |

담당자 실명은 아직 배정되지 않았습니다. `🚧 트랙 A 담당자`, `🚧 트랙 B 담당자`로 두며 배정 시 이 문서를 갱신합니다.

## 경계 원칙

- 트랙 A는 실행을 직접 시작하지 않고 추천 또는 근거 계약을 발행합니다.
- 트랙 B는 추천 근거를 다시 계산하지 않고 전달받은 계약을 기준으로 사용자 확인과 실행을 담당합니다.
- 어느 트랙도 다른 서비스의 데이터베이스나 내부 소스를 직접 사용하지 않습니다.
- 공통 프레젠테이션 및 플랫폼 패키지는 트랙 B가 구현을 주도하되, 공개 계약 변경은 두 트랙이 함께 검토합니다.
- 의견이 갈리면 내부 구현은 담당자 판단을 따르고, 계약 및 구조는 프로젝트 책임자에게 올립니다.
