# Ruple 작업 흐름

## 기본 흐름

| 단계 | 산출물 | 통과 조건 | 책임 |
|---|---|---|---|
| 1. 계약 정의 | 입력, 출력, 오류, 상태 전이, 예시 | 프로젝트 책임자가 사용자 흐름과 모듈 경계를 확인 | 프로젝트 책임자 |
| 2. 모듈 설계 | 내부 구조, 저장 방식, 알고리즘, 테스트 계획 | 공개 계약을 지키고 다른 서비스 내부에 의존하지 않음 | 각 트랙 담당자 |
| 3. 구현 및 검증 | 코드, 단위 테스트, 계약 검증 결과 | 담당 범위 테스트와 `node harness/check.mjs` 통과 | 각 트랙 담당자 |
| 4. 통합 | 연결된 대표 흐름과 배포 산출물 | 현재 커밋에서 전체 점검과 대표 흐름 검증 통과 | 두 담당자 공동 |

## 변경 절차

1. 작업자는 변경 목적, 대상 모듈, 영향받는 계약을 작업 시작 시 명시합니다.
2. 계약에 영향이 없으면 모듈 담당자가 내부 설계를 결정합니다.
3. 계약에 영향이 있으면 구현 전에 `contracts/catalog.json`과 스키마, 예시를 갱신하고 계약 책임자의 확인을 받습니다.
4. 공동 영역을 바꿀 때는 두 트랙 담당자가 영향 범위를 검토합니다.
5. 인계 시 변경 파일, 검증 명령, 결과, 남은 미정 사항을 제시합니다.

계약 작성에는 [초안 생성·검증·등록 안내](../development/contract-authoring.md)를, 담당자 인계에는 [개발자 인계 기준](../development/developer-handoff.md)을 사용합니다. 도구의 형식 검증 통과와 공개 계약 확인은 별도입니다.

## 완료 기준

- 요청 범위의 구현 및 문서 반영
- 관련 단위 테스트와 계약 검증 통과
- `node harness/check.mjs` 통과
- 대표 흐름에 영향이 있는 경우 해당 흐름 검증
- 대상 커밋과 검증 결과의 연결

## 실패 처리

점검 실패는 원인을 해결한 뒤 다시 실행합니다. 오탐으로 판단되면 검사를 우회하지 않고 `harness/policy.json`과 검사 근거를 함께 검토합니다. 임시 우회가 필요한 경우 적용 범위, 만료 조건, 되돌림 방법을 문서화하고 프로젝트 책임자의 승인을 받습니다.
