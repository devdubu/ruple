# 개발자 인계와 기초팀 작업 경계

2026-10-29 기준입니다. 기반 커밋은 `94850ff`이며, 이 문서와 계약 작성 도구는 그 위의 후속 작업 트리입니다. 두 개발자는 각자 격리된 체크아웃·기기·VM에서 설계합니다. 같은 호스트에서 두 트랙을 동시에 띄우는 구성이 아닙니다.

|---|---|---|

| 백엔드 | 설정·인증 연결·오류·추적·입력 검증·OpenAPI·health/ready·정상 종료 | 업무 인가·endpoint·DB probe·작업 처리 |
| 프론트 | 토큰·기본 컴포넌트·화면 등록·앱 셸·API 주입·Query | 기능별 화면·상태·상호작용 |
| 로컬 저장 | 서비스별 PostgreSQL·runtime/migration 역할·Drizzle·기술 예제 데이터 | 자기 업무 모델·SQL·트랜잭션·데이터 수명 |

| 협업 | 계약 템플릿·형식 검사·등록 절차·의존성 검사·CI 정의 | 공개 입출력 초안과 상대 트랙 검토 |

출퇴근 등 업무 흐름의 필드·승인 정책·조건·만료·취소는 기능 담당자가 초안을 작성하고 공동 검토합니다. 작성 방법은 [계약 작성 기준](contract-authoring.md), 역할의 정본은 [담당 경계](../governance/ownership.md)입니다.

## 첫 실행 체크리스트

1. 원격에 전달받은 브랜치·커밋을 체크아웃하고 `git status --short`로 기존 작업을 확인합니다. `94850ff`가 로컬 커밋으로 존재한다는 사실만으로 원격 공개·CI 통과를 가정하지 않습니다.
2. [독립 개발 작업공간](README.md)에 따라 고정 Node·pnpm·의존성을 설치합니다. DB를 사용하려면 로컬 Docker·Compose도 준비합니다.
3. 아래에서 자기 트랙만 실행하고 웹·자기 API의 `/health`·개발 신원·peer의 `x-ruple-mock: true`를 확인합니다.
4. `pnpm check`를 실행합니다. Docker·프로세스 부팅까지 확인하려면 각 테스트가 만드는 로컬 프로젝트와 사용 포트를 확인하고 `test:dev-db`·`test:isolated`를 실행합니다.
5. 자신이 소유할 영역과 필요한 상대 계약을 기록하고, 계약에 영향 없는 내부 설계부터 시작합니다. 공개 필드가 필요하면 템플릿으로 초안을 작성합니다.

```bash
# 트랙 A
pnpm db:up a
pnpm dev:isolated:a

# 트랙 B — A와 별도 환경에서 실행
pnpm db:up b
pnpm dev:isolated:b
```

종료 후 `pnpm db:down a` 또는 `b`로 DB를 중지합니다. 설정·비밀번호는 `local-artifacts/`에 남고 Git에 포함하지 않습니다. 초기화와 역할 상세는 [DB·모의 실행 안내](isolated-development.md)를 따릅니다.

## 트랙별 변경 위치

| 담당 | 주 변경 위치 | 경계 |
|---|---|---|
| A | `apps/context-api`, `apps/ai-api`, `packages/context/{ui,contracts,server}` | B 내부·DB에 직접 접근하지 않음 |
| B | `apps/automation-api`, `apps/automation-worker`, `apps/interaction-api`, `packages/{automation,interaction}/{ui,contracts,server}` | A 내부·DB에 직접 접근하지 않음. B 내부 서비스도 계약으로 연결 |
| 공통 협의 | `packages/{presentation,platform,platform-client,platform-server}`, 웹 셸·CI·공통 설정·등록 계약 | 영향받는 양쪽 담당자와 함께 검토 |

화면은 자기 UI 패키지, 공개 타입은 자기 contracts 패키지, 저장·알고리즘은 자기 server 패키지에 둡니다. 앱은 부팅·조립을 담당합니다. AI 모델·RAG 미구축은 기술 모의 응답을 사용하는 로컬 설계를 막지 않습니다. 현재 모의 서버는 실제 추론 결과를 제공하지 않습니다.

## 설계·변경 인계에 포함할 것

- 목적·소유 모듈·생산자/소비자·변경 파일
- 영향을 받는 공개 계약 또는 계약 영향 없음의 근거
- 상태·저장·동시성·중복·시간·외부 실패·권한 중 해당 항목의 설계
- 검증 명령·대상 커밋·결과·남은 미정과 미검증 항목

현재 기반은 로컬에서 기능 설계를 시작하기 위한 출발점입니다. 두 트랙의 실제 개발자 환경 첫 실행·담당 배정은 아직 확인하지 않았습니다. 아래 운영·통합 작업의 완료를 뜻하지도 않습니다.

| 순서 | 기초팀 작업 | 확인할 결과 |
|---|---|---|
