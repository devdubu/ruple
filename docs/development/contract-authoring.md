# 계약 작성과 공통 기술 기준

두 트랙이 독립적으로 설계하면서 연결 지점만 합의하는 절차입니다. 계약 정본과 버전 규칙은 [계약 관리](../../contracts/README.md), 책임과 변경 절차는 [작업 흐름](../governance/workflow.md)을 따릅니다. 이 문서는 업무 필드·상태·정책을 확정하거나 새 중앙 서비스를 추가하지 않습니다.

## 담당 경계

| 담당 | 결정·산출물 |
|---|---|
| 기초 아키텍처 | 서비스 책임 경계, 공통 기술 원칙·템플릿·검증 도구, 양쪽 계약의 호환성 검토 |
| 상태를 소유한 트랙 | 입력·출력·업무 상태·권한·예외 초안, 자기 저장·알고리즘·화면·시험 설계 |
| 소비 트랙 | 필요한 정보·실패 시 행동 검토, 같은 예시를 사용하는 소비자 시험 |
| 프로젝트 책임자 | 사용자 흐름·공개 계약 확인, 경계 변경·미정 정책 결정 |

트랙 A는 context·AI 영역, 트랙 B는 automation·interaction 영역을 맡습니다. B 안에서도 automation과 interaction은 별도 서비스입니다. 상세 배정은 [담당 경계](../governance/ownership.md)가 정본입니다. 기초팀이 추천 기준·승인 정책·루틴 필드·실행 상태를 대신 정하지 않습니다.

## 작성 → 검증 → 등록

```bash
# 실제로 설계할 경계의 이름을 사용. 업무 필드는 자동 생성하지 않음
pnpm contract:new <contract-id>
pnpm contract:check <contract-id>
```

첫 명령은 `contracts/drafts/<contract-id>/`에 `schema.json`, `examples.json`, `README.md`를 만듭니다. ID는 64자 이내의 소문자·숫자·단일 하이픈을 사용합니다. 이미 등록된 ID나 기존 초안은 덮어쓰지 않습니다.

생성한 스키마의 `not: {}`는 모든 입력을 거부하고 `valid` 예시는 비어 있습니다. 담당자가 실제 구조와 예시를 작성하기 전에는 검사에 실패하는 것이 정상입니다. `0.1.0`도 검토용 시작 버전이며 공개 v1을 승인한 의미가 아닙니다. 도구는 카탈로그·공개 타입·라우터·모의 경로를 수정하지 않습니다.

1. 상태 소유자가 템플릿의 목적·생산자·소비자·호출/이벤트·입출력·오류·미정 항목을 작성합니다. 필드의 의미와 제약을 먼저 합의할 수 있도록 README와 스키마를 함께 작성합니다.
2. 합성 정상·오류·거부 예시를 채우고 `contract:check`로 확인합니다. 호출별 요청과 응답, 오류에 어떤 스키마 또는 `$defs`를 적용할지도 명시합니다.
3. 소비자가 같은 예시로 필요한 정보와 실패 처리를 검토합니다. 프로젝트 책임자의 확인 근거를 초안 문서에 기록합니다. 형식 검사 통과는 승인 기록이 아닙니다.
4. 검토 후 스키마·예시·설명 문서를 정식 경로로 옮기고 ID·버전·owner·schema·example을 `contracts/catalog.json`에 등록합니다. README의 상태·버전·검증 명령도 등록 상태에 맞춥니다. 관련 흐름 문서에서 이 계약을 연결합니다.
5. 등록 스키마를 기준으로 소유 도메인의 `packages/<domain>/contracts`에 공개 타입·검증기를 연결하고, 생산자·소비자 시험과 모의 경로를 작성합니다.

미정 항목은 `🚧`로 남기되, 구현에 필요한 의미가 미정이면 해당 공개 경계 구현을 시작하지 않습니다. 다른 경계·내부 설계·로컬 골격 작업은 계속할 수 있습니다. 이미 등록한 계약 수정은 기존 파일·버전 규칙을 사용합니다.

## 공통 기술 원칙

아래는 계약마다 명시할 기술 원칙입니다. 공통 런타임에 이미 적용한 기능과 도메인 구현 시 추가할 기능을 구분합니다. 모든 명령에 특정 필드나 헤더를 일괄 추가하지 않습니다.

| 항목 | 공통 기준 | 현재 제공 / 담당자 구현 |
|---|---|---|
| 신원·권한 | 서버가 검증한 신원을 사용하고, 리소스 소유권·기기/차량 접근을 별도 확인 | 공통 deny·개발 신원·검증기 연결 제공. 실제 제공자·업무 인가는 후속 |
| 추적·식별 | `x-request-id`는 요청 추적용. 리소스 ID·버전·중복 요청 키와 구분 | 추적 헤더·안전한 로그 제공. 업무 ID 형식·발급 주체는 계약에서 정의 |
| 시각·시간대 | 사건 시각은 UTC로 정규화한 RFC 3339 문자열(`Z` 또는 `+00:00`) 사용. 현지 반복 시각은 지역 시간대와 DST 처리 원칙을 별도로 정의 | Clock 제공. 반복·달력·오차·만료 판정은 도메인에서 정의·시험 |
| 값·부재 | 누락·null·확인된 부재·조회 실패·오래된 값·미지원을 같은 값으로 치환하지 않음. 단위·범위·관측 시각 명시 | DTO 기반 입력 검증 제공. 업무 의미·스키마는 담당자 설계 |
| 변경·동시성 | 변경은 소유 서비스로 요청. 경합 가능한 요청에는 비교할 버전과 충돌 뒤 재조회 방법 명시 | 공통 409 형태만 제공. 버전 비교·원자적 저장은 담당자 구현 |
| 중복·재전달 | 필요한 명령은 키의 사용자/동작 범위·요청 동일성·원자성·처리 중/완료 결과·보존 범위를 정의 | 중복 방지 저장소·미들웨어 미제공. 추적 ID만으로 중복 실행을 막지 않음 |
| 외부 호출 | 의존성별 timeout과 취소 전파 명시. 쓰기·실행은 중복 방지와 결과 확인 없이 자동 재시도하지 않음 | 브라우저 클라이언트 timeout·취소, Query 자동 재시도 해제 제공. 서버 외부 호출은 후속 |
| 응답 불명·취소 | timeout·연결 종료만으로 실패 확정 또는 작업 취소로 판단하지 않음. 재조회와 실제 취소 확인 방법 정의 | HTTP 오류·취소 수단 제공. 업무 결과 조회·취소 상태는 담당자 구현 |
| 상태·전달 | 저장·접수·기기 전달·실제 작업 결과를 구분. 상태 소유 서비스만 전이 확정 | 상태 전이 엔진·큐 미제공. outbox·pg-boss와 재전달 의미는 후속 |
| 저장·종료 | 자기 DB만 사용. 리소스 소유 provider가 DB probe·정상 종료·migration을 연결 | 로컬 DB·Drizzle factory·ready/close 제공. 실제 업무 연결은 후속 |

보존 기간·요청 기한·timeout·재시도 횟수·분석 임계값은 임의의 공통 기본값으로 채우지 않습니다. 이미 제공하는 기술 기본값은 [백엔드 규약](backend-conventions.md)과 [프론트 기반](frontend-foundation.md)을 따르며, 업무별 값은 이유와 검증 근거를 기록합니다.

## 예시와 검증 범위

`examples.json`은 `valid`·`invalid` 배열을 사용하고 각 항목은 고유한 `name`·`value`를 갖습니다. 정상 응답과 스키마에 맞는 오류 응답은 `valid`, 스키마가 거부해야 할 입력은 `invalid`에 둡니다. 공통 HTTP 기술 오류를 그대로 쓸 때는 기존 `platform-http@1.0.0`을 참조했다고 문서에 명시하고, 업무 오류 추가는 별도 계약 검토를 거칩니다.

JSON Schema 검사는 자료형·구조·범위·형식을 확인합니다. 사용자 소유권·버전 비교·중복 실행·시간 선후 관계·상태 전이·트랜잭션은 의미 시험이 필요합니다. 생성한 TypeScript 타입도 수신 JSON을 실행 중 검증해 주지는 않습니다. 생산자는 실제 endpoint 응답을, 소비자는 정상·오류·알 수 없는 응답을 같은 예시와 대조합니다.

현재 `contract:check`는 단일 독립 스키마의 내부 `$defs`·`$ref`를 지원하며 외부 파일 `$ref`를 자동 로딩하지 않습니다. 공통 정의 재사용이 필요하면 참조 로딩·버전 고정·검증 도구 지원을 먼저 검토합니다.

```bash
pnpm contract:check <contract-id> # 등록 전 초안 형식 검사
pnpm check:contracts             # 등록된 계약의 정상·거부 예시 검사
pnpm check                      # 전체 검사와 금지 의존성·개발 도구 시험
```

개발 모의 서버는 `contracts/development/mock-routes.json`에서 **등록된** 계약의 valid 예시만 사용합니다. 현재 registry는 정확한 메서드·경로를 사용하고 공통 경로를 모든 peer에 적용합니다. 서비스별 업무 경로·경로 매개변수·요청/응답별 스키마 검증은 확장이 필요하므로, 파일에 경로를 적는 것만으로 구현됐다고 보지 않습니다. 자세한 실행 범위는 [독립 개발 안내](isolated-development.md)를 따릅니다.

## 계약 인계 조건

- 생산자·소비자·상태 소유자와 확인 근거가 명시됨
- 호출/이벤트별 입력·정상 결과·오류·빈 결과·인증 범위가 정의됨
- 해당하는 버전·중복·시각·만료·취소·응답 유실 처리가 정의되고 의미 시험이 연결됨
- 스키마·예시·공개 타입·실제 생산자/소비자·모의 응답의 버전이 일치함
- 관련 검사 결과에 대상 커밋·작업 트리·미검증 항목이 기록됨
